# 나가치 v21 — 관심 많은 동행 먼저, 없으면 직접 찾기

## 화면 순서와 원칙
1. 상단 메시지는 **“좋은 하루, 같이 갈 사람?”**으로 간소화하고 실사진 히어로 높이를 줄입니다.
2. 홈 상단에 **“요즘 관심 많은 동행”**을 배치합니다.
3. 최근 90일간 동의 후 저장한 관심 중, 특정 장소에서 서로 다른 익명 브라우저가 **5개 이상**인 경우 실제 장소 사진·이름·활동·관심 수 순서로 추천합니다. 버튼을 누르면 기존 장소와 연결된 **동행 관심 남기기** 흐름이 열립니다.
4. 특정 장소별 집계가 아직 없으면 기존 `nagachi_public_interest_counts()`의 실제 **활동별 관심 수**를 높은 순서로 표시합니다. 활동을 누르면 실제 장소 목록으로 이어집니다.
5. 위 두 유형의 실제 집계가 없다면 **가짜 모임/좋아요/모집 인원은 만들지 않고** 음식·산행·산책카페·근교나들이 중 관심 있는 활동을 고를 수 있게 합니다. 실제 장소 636곳을 유지합니다.
6. 모든 인원 수는 **관심 의사 표시자 수**이지 실제 모집/참여 확정 수가 아닙니다. 장소별 고유 브라우저 수이고, 두 활동에 중복 응답한 사람이 있을 수 있으므로 합산해 총인원이라고 주장하지 않습니다.

## 운영 데이터 설정 (무료 Supabase)
1. 기존 `supabase/schema.sql`을 실제 DB에 검토·적용해 `public.record_event(jsonb)`가 현재 연령/활동/서비스비 항목을 받아들이는지 확인합니다.
2. 기존 `supabase/companion-groups.sql`을 실행하면 활동별 공개 관심 수 RPC와 관리자 모임 공지 기능이 생깁니다.
3. **신규** `supabase/popular-companion.sql`을 실행하면 장소별 공개 인기 RPC `nagachi_public_popular_places()`가 추가됩니다.
4. 사용한 SQL은 사용자 ID·이름·연락처·원본 설문 정보를 공개하지 않고, 5개 이상인 장소/활동 조합의 관심 수와 장소 ID만 반환합니다.
5. 이 세 파일은 **운영자가 Supabase SQL Editor에서 직접 실행해야 합니다.** GitHub 소스 병합만으로 운영 Supabase 함수는 설치되지 않습니다. 새 유료 서비스/API는 추가되지 않습니다.

## 실제 저장 오류 확인
사용자가 앞서 보여준 “선택한 정보를 서버에서 받지 못했어요. 운영자가 데이터 규칙을 업데이트해야 합니다.” 문구는 클라이언트에서 **HTTP 400/409/422**로 분류한 저장 실패입니다. 정확한 원인은 실제 Supabase logs 확인 전에는 단정할 수 없지만, DB 스키마가 현재 앱의 40~49세 연령, 복수 `activities`, `willingness` 등을 허용하는지 우선 확인해야 합니다. 
저장 실패가 지속되면 실제 인기도도 표시되지 않습니다. 인기 화면이 **집계 연결 준비 중/아직 관심 없음**을 표시하더라도 임의의 데이터로 채우지 않도록 했습니다.

## 모바일 검수
- Safari에서 첫 화면 위쪽에 짧은 헤더와 인기 카드가 보이는지 확인
- 인기 장소 카드에서 `나도 가보고 싶어요`를 눌러 장소별 동행 선택 열림 확인
- 데이터가 0인 테스트 환경에서 모든 관심 수가 숨겨지고 ‘직접 동행 찾아보기’가 작동하는지 확인
- 홈/하단 메뉴의 ‘같이갈래?’가 인기 동행 영역으로 이동하며 고정 헤더에 제목이 가려지지 않는지 확인
- 실제 저장 성공 뒤 인기 집계는 5명(서로 다른 브라우저) 이상일 때만 표시
- 동행 모임 ‘참가 확정’, ‘모집 중’이라고 표시하지 않음
- GitHub CI 통과는 Cloudflare 배포 및 Supabase 운영 반영 성공을 의미하지 않음
